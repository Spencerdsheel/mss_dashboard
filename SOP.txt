1. OBJECTIVE
================================================================================
1. Provide a multi-tenant analytics dashboard for retail-execution campaign
   data (KPIs, visit records, install-execution rates, photo evidence).
2. Serve three distinct user populations from one codebase:
   a. TENANT_USER - client-side staff viewing their own company's projects.
   b. CLIENT_ADMIN - client-side administrators managing users/projects within
      their own tenant(s).
   c. PLATFORM_ADMIN - internal/platform operators with cross-tenant access
      and system configuration control.
3. Ingest campaign data from the iSN/Shopmetrics provider on a schedule and
   on demand, normalizing it into a single Postgres schema for reporting.
4. Enforce strict tenant isolation so no client can see another client's data,
   regardless of role.
5. Offer admin-configurable dashboard layouts, including an AI-assisted
   layout-suggestion feature gated behind a platform setting.

2. TECH STACK
================================================================================
Frontend
1. Next.js 15.0.3 - App Router, React Server Components (RSC), React
   19.0.0-rc, TypeScript.
2. shadcn/ui + Radix primitives - component library.
3. Tailwind CSS 3.4 - styling.
4. Recharts 2.13 - charts (donut, trend, radar).
5. react-leaflet / leaflet - map view (store locations).
6. zod - runtime schema validation.
7. vitest 2.1 - frontend test runner (tests/*.test.ts, 14 test files).

Backend
1. Python + FastAPI (fastapi>=0.115,<1) - REST API framework.
2. Starlette, pinned >=0.40,<1 - see requirements-backend.txt comment;
   required because prometheus-fastapi-instrumentator 5.11 breaks under
   Starlette 1.x routing.
3. asyncpg - direct async Postgres driver. No ORM is used in the runtime
   query path (services/common/postgres_repository.py uses raw SQL).
4. SQLAlchemy + alembic - present in requirements-backend.txt, but the
   repository's actual data-access pattern is raw asyncpg, not ORM-mediated.
5. Celery 5.3 - asynchronous and scheduled task execution (ingestion).
6. slowapi - rate limiting middleware.
7. cryptography - AES-256-GCM secret encryption (services/common/secrets.py).
8. redis>=5 (client library) - cache, rate limiting, Celery broker, JWT
   revocation list.
9. prometheus-fastapi-instrumentator - metrics endpoint.
10. sentry-sdk - error tracking.
11. anthropic>=0.40 - Anthropic API SDK, used for AI-assisted dashboard
    layout suggestions (added Sprint 14).

Database
1. PostgreSQL 16 - primary data store, schema "dashboard".
2. Access is via asyncpg directly; no ORM layer in the query path.
3. PgBouncer in front of Postgres for transaction-mode connection pooling.

Cache / Broker
1. Redis 7 - response cache, rate-limit counters, Celery broker/result
   backend, JWT revocation/blacklist store.

Auth
1. JWT issued by the FastAPI backend (services/common/security.py,
   create_access_token).
2. Token is stored in an httpOnly cookie set by the Next.js server action
   (src/app/login/actions.ts:23-29) - NOT by the FastAPI backend itself
   (confirmed: zero set_cookie/httponly calls in the backend).
3. Cookie name "auth_token"; maxAge 3600s (1 hour); sameSite lax; secure
   flag enabled in production.
4. src/middleware.ts reads the cookie and redirects unauthenticated users
   away from /dashboard and /admin paths.
5. Every server-side fetch forwards the cookie value as an
   "Authorization: Bearer <token>" header to FastAPI; the backend
   dependency get_current_claims (services/api/dependencies.py) validates it.
6. Logout: POST /auth/logout blacklists the token in Redis, then the
   Next.js action deletes the cookie.
7. Passwords hashed with PBKDF2-SHA256, 120,000 iterations.
8. Provider secrets encrypted at rest with AES-256-GCM
   (services/common/secrets.py); SECRET_ENCRYPTION_KEY is a distinct env
   var from JWT_SECRET.

AI
1. Anthropic API (anthropic>=0.40 SDK) powers AI-assisted dashboard layout
   suggestions (services/api/services/layout_suggestion.py).

Testing
1. vitest - frontend unit/contract tests (tests/).
2. pytest - backend tests (backend_tests/, 17 test modules).

3. SYSTEM DESIGN
================================================================================
There are TWO SEPARATE data-flow paths in this system. They do not share a
request lifecycle: the read path serves already-ingested data; the ingestion
path is what populates it. Do not conflate them.

3.1 Request-time read path (numbered)
1. Browser requests a dashboard page (a React Server Component).
2. The page calls src/server/analytics.ts getProjectSummary(), forwarding the
   JWT from the httpOnly cookie as a Bearer header.
3. This calls GET /projects/{id}/summary, handled in
   services/api/routes/projects.py.
4. The route handler calls services/common/postgres_repository.py
   get_project_summary(), passing explicit tenant context.
5. postgres_repository.py runs tenant-scoped SQL (CTEs: visit_stats,
   photo_stats, install_distributions) against Postgres schema "dashboard".
6. The result is shaped into a ProjectSummary object and serialized back to
   the frontend.

3.2 Ingestion path (separate process, numbered)
1. Trigger is one of two sources:
   a. Celery Beat's scheduled job "scheduled-tenant-refresh", interval set
      by SCHEDULED_REFRESH_INTERVAL_MINUTES (default 360 minutes / 6 hours;
      see services/ingestion/celery_app.py).
   b. An admin manually calling POST /admin/tenants/{id}/refresh
      (services/api/routes/admin.py).
2. Both paths dispatch the Celery task run_tenant_refresh
   (services/ingestion/tasks.py).
3. The task fetches the tenant's active provider_connections row and
   decrypts its client_secret_encrypted field.
4. services/ingestion/client.py ShopmetricsClient authenticates via OAuth2
   client_credentials against the provider (real iSN/Shopmetrics API in
   production, or the local mock server in dev).
5. services/ingestion/extractor.py ShopmetricsExtractor.pull() retrieves 12
   resources (7 reference rowsets + 5 transactional rowsets).
6. services/ingestion/transform.py transform_shopmetrics_rowsets() normalizes
   the rowsets into DashboardVisit / DashboardPhoto / DashboardMetric objects.
7. services/ingestion/persistence.py load_transformed_dataset() performs an
   idempotent UPSERT into dashboard.visits / dashboard.visit_photos, keyed on
   (tenant_id, project_id, survey_id). Re-running ingestion cannot duplicate
   or mint new rows by design.
8. On success: a run_logs row is written, provider_connections.last_sync_at
   is updated, and the tenant's Redis cache entries are invalidated.
9. On failure: the task retries up to 3 times with exponential backoff
   (60 * 2^retries seconds), then writes a "failed" run_logs row.

3.3 Role model and project visibility
1. Roles (services/common/models.py Role enum): PLATFORM_ADMIN, CLIENT_ADMIN,
   TENANT_USER. A legacy two-role ADMIN/CLIENT model was migrated via
   migrations/001_add_companies.sql.
2. src/server/rbac.ts requireAdmin() permits PLATFORM_ADMIN only.
3. src/server/rbac.ts requireAdminOrAbove() permits PLATFORM_ADMIN or
   CLIENT_ADMIN.
4. listVisibleProjects() scopes by role:
   a. PLATFORM_ADMIN sees all projects across all tenants.
   b. CLIENT_ADMIN sees projects across their own tenantIds.
   c. TENANT_USER sees only projects under their own clientId.

3.4 Tenant isolation (mandatory, not optional)
1. tenant_id is derived only from verified JWT claims - never from query
   strings, request bodies, route params, or headers.
2. Every database-layer function takes an explicit tenant context argument
   and filters on it (services/common/postgres_repository.py).
3. There is no "global" read path except explicit PLATFORM_ADMIN-role
   operations with an explicit role check.

4. HOW TO RUN LOCALLY
================================================================================
Prerequisites
1. Conda environment named exactly "venv" must exist and be used for ALL
   python, pip, pytest, uvicorn, and celery commands. Activate it first:
   conda activate venv

Startup sequence (numbered, run in order)
1. docker compose up -d
   Starts three local infra containers:
   - postgres:16 on host port 5433 (db shopmetrics_demo, user postgres,
     password admin)
   - pgbouncer on host port 5434 (transaction-mode pooling in front of
     Postgres; MAX_DB_CONNECTIONS=90, kept under Postgres default
     max_connections=100)
   - redis:7 on host port 6380
2. npm install --legacy-peer-deps
   Installs frontend dependencies.
3. conda activate venv
   pip install -r requirements-backend.txt
   Installs backend dependencies inside the "venv" conda env.
4. cp .env.example .env
   Edit as needed. REDIS_URL / DATABASE_URL in .env.example already point
   at the nonstandard local ports above.
5. conda activate venv
   uvicorn services.api.main:app --reload --port 8010
   Starts the backend API on port 8010. Database migrations auto-apply at
   startup via services/ingestion/migrate.py inside the FastAPI lifespan
   handler (services/api/main.py).
6. npm run dev
   Starts the frontend on port 3000 (uses --turbopack).
7. Open http://localhost:3000

Additional / optional processes (not started by the above)
1. Standalone mock iSN/Shopmetrics provider server:
   python -m services.api.client_server
   Default port 8020. This is a SEPARATE process from the main API, is NOT
   registered in services/api/main.py's routers, and is explicitly marked
   in client_api.py as development/single-process-only with in-memory
   state. Not for production use.
2. Celery worker (Windows syntax - required due to --pool=solo on Windows):
   celery -A services.ingestion.celery_app worker --loglevel=info
   --pool=solo --concurrency=4
   Migrations also auto-apply on Celery worker startup via the worker_init
   signal (services/ingestion/celery_app.py).
3. Manual migration check/apply:
   python -m services.ingestion.migrate --dry-run
   (omit --dry-run to apply for real)

Verification gates (run before declaring any change complete)
1. Frontend: npx tsc --noEmit
2. Frontend: npm run lint
3. Frontend: npm test   (vitest, 14 test files in tests/)
4. Backend: conda activate venv && python -m pytest backend_tests -v
   (17 test modules in backend_tests/)

5. FEATURES
================================================================================
1. Live project dashboards: KPIs, install-execution donut charts, visit
   counts, date-range summaries, rendered server-side.
2. Per-project campaign model with 1-4 configurable "install slots"
   (project_install_slots / project_install_categories tables).
3. Visit-level drill-down: filterable, cursor-paginated visit list
   (GET /projects/{id}/visits) with photo evidence per visit
   (GET /projects/{id}/visits/{instance_id}/photos).
4. Locations view: map-based store location view per project
   (src/app/dashboard/projects/[projectId]/locations/).
5. Admin tooling under /admin: companies management, tenant/provider
   connection config, user management (create/edit/role/password-reset),
   project management, photo-slot label editing, project metrics editing,
   platform settings (branding), ingestion run history (run_logs), manual
   refresh trigger.
6. Scheduled and on-demand ingestion refresh via Celery (see Section 3.2).
7. AI-assisted dashboard layout suggestion:
   - services/api/services/layout_suggestion.py
   - Invoked via POST /admin/projects/{id}/dashboard-layout/suggest
   - Uses the Anthropic API (settings.anthropic_api_key)
   - Gated by a platform_settings key ai_layout_generation_enabled, an
     admin on/off toggle distinct from the 503 response returned if
     ANTHROPIC_API_KEY is simply unset.
8. Customizable dashboard widget layouts:
   - dashboard_layouts table, keyed per project + page_key
   - Widget registry constrained by an allowlist
     (services/common/allowed_widget_types.json)
   - Two coexisting layout systems: a v1 preset layout system and a v2
     "freeform" drag/resize layout mode
     (services/common/freeform_layout_schema.py)
9. Password reset flow: hashed, single-use, expiring tokens
   (password_reset_tokens table); redeem page at /reset-password.
10. Three-tier RBAC (PLATFORM_ADMIN / CLIENT_ADMIN / TENANT_USER) - see
    Section 3.3.

   CLIENT_ADMIN

    CLIENT_ADMIN

    PLATFORM_ADMIN or CLIENT_ADMIN

    directly visible in page.tsx header; exact required role not
    independently confirmed this pass

10. GLOSSARY
================================================================================
1. JWT (JSON Web Token) - a signed token carrying claims (subject, tenant,
   role, project access) used to authenticate API requests.
2. RBAC (Role-Based Access Control) - authorization model that grants
   permissions based on a user's assigned role.
3. RSC (React Server Components) - React components that render on the
   server and ship no client-side JavaScript unless explicitly marked
   interactive.
4. Celery - a distributed task queue used here to run scheduled and
   on-demand ingestion jobs outside the request/response cycle.
5. PgBouncer - a lightweight connection pooler placed in front of
   PostgreSQL to limit and reuse database connections under load.
6. Idempotent ingestion - re-running an ingestion job produces the same
   end state as running it once; it does not duplicate or mint new rows.
7. Tenant isolation - the guarantee that one client/tenant's data is never
   visible to, or mixed with, another tenant's data.
8. httpOnly cookie - a cookie flag that prevents client-side JavaScript
   from reading the cookie's value, mitigating token theft via XSS.
